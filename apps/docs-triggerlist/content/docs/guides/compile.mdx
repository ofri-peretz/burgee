title: Compile REVIEW.md
description: "triggerlist compile writes REVIEW.md from the checklist, one line per rule with a link to why it exists, under a byte budget; --check fails when the file is stale, and an over-budget run names the least-fired rules to drop."
---

```bash
npx triggerlist compile [--check] [--budget <bytes>] [--firings <file>] [--out <path>] [--checklist <path>]
```

`REVIEW.md` is the whole rulebook in one file: what a reviewer reads in full, and what
[`brief`](/docs/guides/brief) puts at the top of every prompt. `compile` generates it from the
checklist so the two never disagree. It reads the checklist from the working tree, since it
writes a file you commit.

## Writing it

```text title="npx triggerlist compile"
wrote REVIEW.md, 3 rule(s), 850 of 150000 bytes
```

It writes:

```md
# REVIEW.md

Generated by `triggerlist compile` from `.sdlc/checklist.yaml`. Do not edit it by hand: edit the checklist and compile again.
CI reads this file and the checklist from the base branch, so a pull request is always reviewed by the rules it did not write.

The reviewer is shown only the rules whose triggers fire on the diff (`triggerlist match <base>`), each with the check that answers it. Every rule:

- `spawn-through-helper` Does new code spawn a process directly instead of through src/run.ts? ([why](https://github.com/acme/app/pull/212))
- `migration-has-down` Does every new migration have a matching down migration? ([why](docs/decisions/0007-reversible-migrations.md))
- `no-console-in-lib` Does library code print to the console instead of returning or logging through the logger? ([why](https://github.com/acme/app/pull/318))
```

Run it again with nothing changed and it says `unchanged:` and writes nothing. The header line
says where the file came from; every rule is its `id`, its question and a link to its first
source.

## Keeping it current

`--check` writes nothing and exits 1 when the file on disk differs from what the checklist
compiles to. Put it in CI or a pre-push hook so a checklist edit cannot land without its
`REVIEW.md`:

```yaml title="one-rule.yaml"
gates: []
items:
  - id: spawn-through-helper
    trigger: { paths: ["src/**/*.ts"], pattern: "child_process" }
    question: Does new code spawn a process directly instead of through src/run.ts?
    check: a child_process import outside src/run.ts is a finding
    sources: ["https://github.com/acme/app/pull/212"]
```

Checked against the three-rule `REVIEW.md` written above, a checklist with only this one item
fails:

```text title="npx triggerlist compile --check --checklist one-rule.yaml" exit="1"
REVIEW.md is not what the checklist compiles to. fix: run `triggerlist compile` and commit the result
```

## The budget

A reviewer has a limit on how much of its instructions it reads, and rules past the limit are
dropped without a word. So `compile` refuses to write a file over `--budget` bytes (150,000 by
default, the limit recorded in `src/compile.ts` for the review tool the file feeds) and says
which rules to drop instead. The design notes in `.sdlc/intents/triggerlist/spec.md` record a playbook
that measured about 535 KB of rules against that 150 KB limit, which is why the reviewer is shown
only what fires rather than every rule.

The three-rule checklist from [Getting started](/docs/getting-started) compiles to 850 bytes.
Under a 750-byte budget:

```text title="npx triggerlist compile --budget 750" exit="1"
REVIEW.md would be 850 bytes, over the 750-byte budget. fix: drop the least-fired rules: no-console-in-lib
```

Without counts, every rule has fired zero times, and among equals the later rule goes first: it
was added last.

## Dropping what fires least

`--firings` takes a JSON object of how many times each item fired, the counts
[replz](https://replz.interlace.tools/docs) reports. The rules that fire least are
named first:

```json title="firings.json"
{ "spawn-through-helper": 9, "no-console-in-lib": 12 }
```

```text title="npx triggerlist compile --budget 750 --firings firings.json" exit="1"
REVIEW.md would be 850 bytes, over the 750-byte budget. fix: drop the least-fired rules: migration-has-down
```

`migration-has-down` has no count, so it is zero, and it is the one to drop. Removing a rule is
still your edit to the checklist; `compile` only names it.

## Options

| Option | Default | What it does |
| :-- | :-- | :-- |
| `--checklist <path>` | `.sdlc/checklist.yaml` | The checklist to compile. |
| `--out <path>` | `REVIEW.md` | The file to write or check. |
| `--budget <bytes>` | `150000` | The most bytes the file may be. |
| `--firings <file>` | none | Firing counts per item id, to choose which rules to drop. |
| `--check` | off | Write nothing; exit 1 when the file is stale. |

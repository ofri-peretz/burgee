**This page is maintained by hand, and that is the reason to distrust it most.** Four of
its rows disagreed with the suite that now measures them — an installed size 5.4x under,
an import cost that flattered us by 12 ms, a claim that burgee landed level with cac
against a measured 1.45x, and a compatibility count of 1,361 that has been
1,360 since the oracle's baseline was set. [Benchmarks](/docs/benchmarks) is generated from `npm run bench` and is the
authority; this page exists to put six frameworks in one table, which that one does not
do, and every cell here now says where it comes from.

- **⚙️ measured** by `npm run bench` on this repo, all four packages in one run on one
  machine, at the date below.
- **📖 surveyed** in [`competitor-landscape.md`](https://github.com/ofri-peretz/burgee/blob/main/.sdlc/research/competitor-landscape.md)
  §2 on a different machine at a different time. Never compare a ⚙️ against a 📖 — that is
  a comparison between two machines.

never for gating; the machine-independent figure is the ratio on
[Benchmarks](/docs/benchmarks).

| | **burgee** | commander | yargs | @oclif/core | cac | citty |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| Downloads / week | new | 508.2M | 259.3M | 10.9M | 49.4M | 30.5M |
| Runtime dependencies | **0** | 0 | 6 | **18** | 0 | 0 |

Three things in that table got worse when they were measured rather than asserted, and
they stay in it.

**Installed size.** burgee installs at **1076 KB**. It is our largest number, it is our least
flattering one, and it has now been wrong on this page twice in opposite directions.

First it said 104 KB, a guess at the tarball rather than a measurement. That was corrected
to **561 KB** on 2026-09-09 — the real `npm pack` unpacked size, which is what lands in a
user's `node_modules` — and then the package grew to **2.3x that figure** while the cell sat
still, because the cell was read from a *published* measurement rather than from a fresh
install. Every check on this page compared the page against that file and stayed green.

Fixed 2026-09-16: the row is now measured against the tree by CI on every run, so it cannot
fall behind again. It is checked there and not on a developer's laptop for a reason worth
stating, since it is the same class of mistake: the walk starts at a workspace link, so
locally it counts a developer's dev dependencies too and reads **1311 KB** for the same
commit. 991 KB is what `npm i burgee` gives you.

**85 KB of it arrived on 2026-09-17 and is worth naming.** `burgee/commander` now spawns
sub-binaries through `bellpull` instead of `node:child_process`, so burgee installs bellpull's
whole package — 86,113 bytes. What it buys is a Windows subcommand that actually works: upstream
commander sends every Windows spawn through `node`, which is a workaround for `spawn` not
searching `PATHEXT`, and it is simply wrong for a subcommand that is a `.cmd`, a `.bat`, or has
a shebang that is not node. The check on this row is what surfaced the cost, which is the
argument for the check.

It buys no dependency outside this repository and six drop-in front ends. It is still 1076 KB, and the
bundled column on [Benchmarks](/docs/benchmarks) — what an application actually grows by —
is the number to judge us on. That one is over its own ceiling too, and says so.

**Speed.** This page previously ran two rows, an import cost and a full run, with burgee's
cells in both unsourced. The suite times one thing, a full CLI run as a process, so there
is one row. burgee does **not** land level with cac: it starts at **1.32x** cac's cold
start against a published target of at or below cac, and that target is recorded as not
met. It is faster than yargs — measurably, 0.82x — and level with commander at 1.08x.

These are the figures from the CI runner, which is where the suite now publishes from: the
same commit measured eleven times there put `burgee ÷ cac` inside 2.3%, where a developer
laptop under load spread the same ratio from 1.351 to 1.957 in a single day. The absolute
milliseconds are a property of that machine and are not comparable with the two 📖 columns,
which come from a survey on somebody else's. **The ratios are what the gates and bands
watch**, because a ratio taken between two spawns in the same run cancels the machine out.

Moving to that machine did not uniformly flatter us. `burgee ÷ cac` improved from 1.45x to
1.32x and commander went from a small loss to a level result; `burgee/yargs ÷ yargs` moved
against us, from 0.69x to 0.82x. The machine was chosen for its variance, before these
numbers were read.

burgee's speed comes from `node:util.parseArgs` being in the standard library, not from a
faster language: burgee is TypeScript, exactly like commander and yargs. That buys parity
with commander, not a lead over cac.

`@oclif/core`'s **131 ms** is a surveyed number, not one this suite reproduces, and it is
carried here rather than dropped because eighteen runtime dependencies against zero is the
comparison this table exists for. Treat it as the survey's, not as ours.

## The three that matter

**Plugins.** commander has no plugin system — its RFC has been open for years — and yargs
has none either. burgee has one, and it works on a program written in *commander's* syntax:
change one import and you gain a capability commander cannot sell you at any price.

**Nothing you rely on breaks.** Compatibility is graded by commander's own 1,360 tests and
yargs' 804, run in our CI, published as a pass rate that only goes up. Not the word
"compatible" — a number you can check. (This paragraph said 1,215 and the table said 1,361;
both were wrong, and the count the oracle's baseline actually holds is 1,360. It is on
[Benchmarks](/docs/benchmarks), where it is read from the oracle rather than retyped.)

**One declaration, every surface.** Help, `--json`, `--schema`, `--mcp`, completions and
types are all projections of the same manifest, so they cannot drift, and adding the next
one is an emitter rather than a feature.

## What we do not have

**Users.** commander and yargs do 767M downloads a week between them; burgee is days old.
Every number above is real and none of it matters until someone installs it. The
compatibility burn-down is published from the first commit precisely so that gap is visible
rather than glossed.

## Reproducing

The ⚙️ rows come from the suite, not from a shell loop, because a shell loop measures
whatever else the machine was doing:

```bash
git clone https://github.com/ofri-peretz/burgee && cd burgee
npm install && npx turbo run build
npm run bench -- --check
```

That writes `benchmarks/results/cli-benchmarks/<date>.json`, which carries every number on
[Benchmarks](/docs/benchmarks) along with the resolved version and path of every package it
measured. The 📖 rows are not reproduced by it; they are
[`competitor-landscape.md`](https://github.com/ofri-peretz/burgee/blob/main/.sdlc/research/competitor-landscape.md)
§2's, taken on a different machine.

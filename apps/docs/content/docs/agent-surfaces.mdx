---
title: Your CLI is an agent tool
description: Every burgee program answers --schema and --mcp from its one declaration — no tool definitions, no second interface.
---

A burgee program is data first. The same manifest that renders `--help` answers two
questions an agent asks before anything else.

## `--schema` — the program as data

```bash
mytool --schema
```

Prints the commands, their arguments and options (with choices, defaults and which are
required), each command's `effects`, its examples, and a JSON Schema per command. It reads
the manifest and nothing else: no config file, no network, no handler runs (N8), so it is
safe to call first.

The document shows each option's default and env var, but not which of them a run used. So
just before `commands` it carries one line naming the flag that answers that:
`"explain":"--explain <option> on a command says where its value came from: default, env, config or flag"`.
Agents that read `--schema` without it spent three to eight turns probing the env var through
shell calls (D-20261009-b1-totals-and-explain). One command's schema (`mytool deploy --schema`)
does not carry it, and neither does `--schema` on `burgee/commander` or `burgee/yargs`, which
do not parse `--explain`.

`mytool schema` is the same request spelled as a subcommand — `schema deploy` and
`schema deploy --field options.region` print exactly what the flag forms print — because
that is where [clispec.dev](https://clispec.dev) and the agents that follow it look. A
program whose own `schema` command exists, or whose root command takes arguments, keeps the
word: burgee answers only the flag there. The root `--help` names `--schema`.

## `--mcp` — the program as MCP tools

```bash
mytool --mcp
```

Serves the same manifest as [MCP](https://modelcontextprotocol.io) tools over stdio —
JSON-RPC 2.0, four methods (`initialize`, `ping`, `tools/list`, `tools/call`), no dependency outside the burgee family. A tool call runs the command exactly as a
`--json` caller would; the result is that envelope, byte for byte, so an agent reading
your CLI over MCP and one shelling out with `--json` see one payload.

### What becomes a tool

Every command that runs and is not hidden, named by its path — `config get` is
`config_get`, and a program whose root command runs (a single `run(defineCommand(…))`, or
a commander program with a root `.action()`) is named after the program. What keeps a
command out is a word its author wrote, never silence:

```ts
defineCommand({
  name: 'deploy',
  effects: 'non_idempotent', // read_only | idempotent | non_idempotent | withheld
  // …
});
```

- **On burgee's own API, `effects` is required.** `defineCommand` refuses a runnable
  command without it, so every tool carries MCP's `readOnlyHint`, `idempotentHint` and
  `destructiveHint`, generated from the declaration. `'withheld'` serves the command to
  people and keeps it out of `tools/list`.
- **On `burgee/commander` and `burgee/yargs`, a command that declared nothing is still a
  tool.** Neither incumbent has a notion of effects, so it is listed with
  `annotations: { effects: 'undeclared' }` and no hints — and MCP's defaults for absent
  hints (not read-only, destructive) are the reading a client applies. Declare it with
  `.effects('read_only')`, or keep it out with `.effects('withheld')`.

### Arguments

A tool's `inputSchema` has one property per argument and option. An option's property is
its declared key and names the flag it becomes — `"dryRun": { "type": "boolean", "flag":
"--dry-run" }` — and a tool call is turned back into exactly that flag. A boolean sent as
`false` is passed as `--no-<name>` when the option would otherwise be on (a `true` default
or an environment variable) and left out otherwise, so an agent that spells out every
`false` trips no relation. Under `burgee/commander`, a `--no-color` declared without a
`--color` is the property `noColor`.

### Results

The `--json` envelope, byte for byte. Under `burgee/commander`, `data` is what the action
**returned**: an action that prints instead gives `data: null`, because commander actions
return nothing. Return the value — `.action(() => ({ lines }))` — and it is `data`.
Printed output becomes the tool result: whatever a handler writes to stdout during a call
(`console.log`, `process.stdout.write`) is captured and follows the envelope as a second
text item, never a stray line on the JSON-RPC stream, and what it writes to stderr stays on
stderr.

A handler that throws, rejects or throws something that is not an `Error` is an error
result, not a crashed server: `isError: true`, and the text is the `{ "ok": false, "error":
… }` envelope a `--json` caller gets on stdout. An `AuthError` carries `code` 5 (`"auth"` on
the commander and yargs front ends) with its `hint` and `fix`, and the server answers the
next call.

### Client configuration

For Claude Desktop, Claude Code, Cursor or any stdio client, register the program as a
server — nothing else to write:

```json
{
  "mcpServers": {
    "mytool": {
      "command": "npx",
      "args": ["mytool", "--mcp"]
    }
  }
}
```

On `burgee/commander` and `burgee/yargs`, a program that declares its own `--schema` or
`--mcp` option keeps it, and burgee leaves it alone: the surfaces are additive, never a change
to a program that already exists. On burgee's own API the names are reserved, and
`defineCommand` refuses an option that redefines one.

## `completion <shell>` — static unless you ask

```bash
mytool completion zsh > "${fpath[1]}/_mytool"   # also: bash, fish, pwsh, fig
```

Commands, subcommands, options and choice values, with descriptions where the shell shows
them — generated from the same manifest, as plain shell. Pressing TAB does not execute the
program, with one exception you opt into: an option that declares `complete` has its values
asked for at TAB time, through `mytool __complete`. Each script is pinned by a snapshot and
exercised by its real shell in CI. The templates live in `burgee/completions` and load only
on that command, so a program pays for them when it prints a script, never at startup.

## `--explain <option>` — where a value came from

Every value a command sees comes from exactly one place, in one fixed order:
**flag > env > config file > package.json field > default**. `--explain` says which, and
what it beat:

```text
$ mytool deploy --explain region
region = "eu-1"   from config file ./mytool.config.json
         candidates: flag --region (unset), env MYTOOL_REGION (unset), default "us-1"
```

Every command that runs lists `--explain <option>` in its help, and the root help's `For
agents:` line names it beside `--schema` and `--json`. So do the `--schema` document and the
hint on an unknown command that matches nothing. The same information rides under `--json` as `meta.provenance`, per option — for an agent,
the difference between one call and five. `envPrefix` and `config: true` on
`defineProgram` opt a program into env names and config discovery; nothing is read that
the running command did not declare.

## Stopping instead of prompting

`ctx.interactive` is true only with a terminal on stdin, no `CI`, and no detected agent
(`AI_AGENT`, `CLAUDECODE`, `CURSOR_AGENT`, `CODEX_THREAD_ID`, `GEMINI_CLI`), terminal or not;
`FORCE_TTY=1` overrides. It is roundel's `interactive()`, the same rule caique's prompts ask. A
handler reads `ctx.interactive` and `ctx.agent`, and where it would have prompted it stops with
what the caller must do:

```ts
if (!ctx.interactive) ctx.actionRequired({
  reason: 'confirm',
  message: 'deploying to prod needs confirmation',
  next: [{ command: 'deploy --target prod --yes', when: 'once you have reviewed the plan' }],
});
```

The envelope carries `status: "action_required"`, the reason, and `next[]` as runnable
commands with the program in front and the caller's own `--json` carried; the exit code is
4. An idempotent command reports `changed: true | false`, and `--schema` summarises above
a character budget with `<command> --schema` to drill into one.

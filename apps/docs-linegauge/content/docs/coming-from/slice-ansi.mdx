**linegauge** is a **slice-ansi alternative** you adopt by changing one import.
`linegauge/slice`'s default export is `slice`, call-compatible with slice-ansi's default, and
slice-ansi's own test suite is the grade.

## Migrate from slice-ansi in one import

```diff
- import sliceAnsi from 'slice-ansi';
+ import sliceAnsi from 'linegauge/slice';
```

The call is slice-ansi's — `sliceAnsi(string, start, end)`, in display columns, `end`
optional. The same function is also the named export `slice`, from `linegauge/slice` or from
`linegauge`.

It also answers the questions slice-ansi's neighbours do, one subpath each:

| Incumbent | linegauge path |
| :-- | :-- |
| `string-width` | `linegauge` (the default export) |
| `strip-ansi` | `linegauge/strip` |
| `wrap-ansi` | `linegauge/wrap` |
| `slice-ansi` | `linegauge/slice` |

## Is linegauge compatible with slice-ansi?

Graded, not claimed. slice-ansi's own suite, vendored at 9.0.1 and unmodified apart from the
import specifier, runs against `linegauge/slice` beside a control that runs it against the
real slice-ansi:

| | passing | rate |
| :-- | --: | --: |
| `linegauge/slice` | 104 / 104 | 100.0% |
| slice-ansi itself (control) | 104 / 104 | 100.0% |

From [Compatibility](https://burgee.interlace.tools/docs/compatibility), which `npm run compat:page` generates from the
oracle's last run; that page is the authority.

Where a cut lands, `slice` counts as slice-ansi does: every cluster takes at least one
position, so CRLF or a zero-width character can start or end a range, and a lone regional
indicator (`🇦`) takes two. `width` still answers as string-width does (0 and 1 for those two),
because it reports what a terminal draws. The two disagree only on clusters that draw nothing.

slice-ansi 7's suite is graded too, at 14 / 15, and 7 is not claimed. The one it fails is the
case where 7 and 9 contradict each other: 7 wants a wide character that runs one column past
the end of the range included, and 9 wants it left out. linegauge leaves it out.

The same page grades `linegauge` against string-width (233 / 233), `linegauge/strip` against
strip-ansi (8 / 8) and `linegauge/wrap` against wrap-ansi (85 / 85).

## What you gain over slice-ansi

slice-ansi 9.0.1 depends on `ansi-styles` and `is-fullwidth-code-point`, which brings
`get-east-asian-width`. `linegauge/slice` depends on nothing, and it is pure: nothing in
linegauge reads `process`, so the same input slices the same way on a pipe, under `--json` and
in a test.

- **A cluster is never halved.** Columns come from the same `width` that passes
  string-width's suite 233 / 233, and cluster boundaries from the platform's own
  `Intl.Segmenter`. A cluster that straddles either edge is left out whole, so a slice is never
  wider than the columns asked for and never returns half a family emoji or one letter of a flag.
- **One style stack, not two.** slice-ansi and wrap-ansi each carry their own copy of
  open/close/reopen, and they disagree at the edges. `linegauge/slice` and `linegauge/wrap`
  share one, so slicing and wrapping the same styled string agree.
- **The family measures with it.** burgee, caique and flagstaff build on linegauge, so what
  they write for a pipe or an agent is cut the same way.

## When to switch from slice-ansi

- Your output carries terminal hyperlinks, and a slice of it has to keep them.
- Your dependency tree carries slice-ansi beside string-width, strip-ansi or wrap-ansi, and
  you would rather it carried one package with no dependencies.

The API and the design notes are on [linegauge](/docs); the width path is on
[Coming from string-width](/docs/coming-from/string-width).

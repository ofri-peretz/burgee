## Requirements

- **R1 — Each task declares the modalities it can be stated in.** `benchmarks/tasks/*.json`
  gains `modalities: ["cli"] | ["cli", "mcp"]`. A task gets `"mcp"` only when its prompt, its
  check and its exemplar hold word for word for an agent that has the demo's tools and no shell.
  `benchmarks/tasks/README.md` records the reason beside each `["cli"]`-only task. A lock
  refuses a task file without the field.
- **R2 — A `burgee-mcp` variant.** `VARIANTS` in `benchmarks/axes/agent.ts` gains
  `{ id: 'burgee-mcp', bin: <the burgee demo>, floor: true, modality: 'mcp' }`. Its spawn:
  1. writes a scratch `mcp.json` naming the demo's `--mcp` server, generated by
     `mcp-current` R6 rather than hand-written: the server's name and arguments as the demo
     prints them, and as its command the build under test (the shim the CLI arms run, by
     absolute path), never a bin name left to whatever `PATH` resolves;
  2. passes `--mcp-config <file>` beside the existing `--strict-mcp-config`;
  3. allows only the demo's MCP tools.

  Everything else is the existing spawn: model, pinned `claude`, turn limit, isolation flags,
  transcript capture.
- **R6 — No run of the arm without its server.** Added 2026-10-26, after the first paid run of the
  arm never reached its server
  ([D-20261026-b1-mcp-arm-server-guard](../../decisions/D-20261026-b1-mcp-arm-server-guard.md)).
  1. Before the arm's first run, the harness starts the server its config names, the way a
     client does, and asks for its tools. A server that lists none breaks the arm, the reason is
     the server's own exit status and stderr, and no paid run is spent.
  2. A run counts only when `claude`'s `init` event reports the server `connected`. Otherwise it
     is a failure of kind `mcp-unavailable` and is in no median, whatever it answered.
  3. A broken arm, any run without the server, or a success rate under the CLI arms' 0.8 floor
     leaves the arm's success rate and reason, ungated, and no ratio. The CLI arms' reading still
     lands.
- **R3 — Medians and ranges, never one run.** Per mapped task and pooled, the arm reports median
  tokens, median turns, the minimum and maximum of each, the success rate, and the run count.
  The ratio `burgee-mcp ÷ burgee` is computed over the same task set only. A claim
  `cli-vs-mcp-tokens` in `benchmarks/claims.ts` stays `unmeasured` until four readings exist, and
  then takes its verdict from the median of the readings' ratios.
- **R4 — The cost is bounded in the workflow.** `bench.yml` runs the arm on `schedule`, on the
  `bench:agent` label, and on a manual dispatch whose `mcp-arm` input is set (added 2026-10-27,
  [D-20261027-b1-mcp-arm-owner-dispatch](../../decisions/D-20261027-b1-mcp-arm-owner-dispatch.md)),
  only. A push to `main` and a dispatch without the input run the two existing variants. A test
  over the workflow file holds that condition, so a later edit cannot widen the spend by accident.
- **R5 — Published, both ways.** `what-an-agent-sees.mdx` gains a "CLI and MCP, one declaration"
  section citing each reading by run id, with the median and range of the four. Every number on it is checked by
  `scripts/agent-page-lock.test.ts` against the landed results files. The section says which
  tasks were excluded and why. `cli-mcp/intent.md`'s fourth criterion is updated with the run ids.

## Design

**Order:** R1 (the task files, no runs), R2 and R4 together (the variant cannot land without the
bound), R3, then R5 after the fourth reading.

**Why the arm is cheap to build.** Everything that makes B1 trustworthy already exists:

- the isolation flags that keep the owner's own `~/.claude` out of the run;
- the pinned `claude`;
- per-run transcripts and redaction;
- the loud skip without a credential;
- the claim and band machinery.

The arm is a variant row, a spawn branch and a workflow condition.

**What counts as one variable.** The CLI arm's agent reads `--help` and `--schema` through Bash.
The MCP arm's agent reads `tools/list`. That difference *is* the comparison: the tool definitions
an MCP client loads before work starts, against the help a CLI agent fetches on demand. It is
what `migration-drivers.md` §6 argues and nobody has measured. Everything else is held equal.

## Rejected alternatives

- **Run the arm on every push to `main`.** +25 paid runs per merge, for a number that needs four
  readings to say anything. Weekly gives the same evidence at a quarter of the cost or less.
- **A separate MCP-only benchmark with its own tasks.** It changes two variables at once. The
  point of the arm is that only the surface differs.
- **Compare against a hand-written MCP server for the same tool.** It would measure the author
  of that server. The same declaration served both ways is the control nobody else can run.
- **Adapt `non-tty-required` for MCP.** A task restated for one arm is a different task. It is
  excluded and named.

## Out of scope

- Other models, other agent clients, and cross-host comparisons (`cli-benchmarks` rejected
  multi-model leaderboards).
- The commander arm over MCP. commander has no `--mcp`, and the incumbent demos get none
  (`cli-mcp`).
- Any marketing claim before R3's four readings exist.

Built 2026-10-12 without a paid run. Every check above went red on the unbuilt code first and was
proved against a stub `claude` and a stub MCP server, the same offline path B1's own harness uses.

- **R1.** Three of the five tasks map: `diagnose-provenance`, `discover-subcommand` and
  `structured-output`. `recover-failure` asks for an exit status and a command line and checks for
  the flag spelling `--code`; `non-tty-required` tests a terminal behaviour. Both are `["cli"]`, and
  `tasks/README.md` says why beside each. The two mapped tasks whose exemplar named a shell command
  have a surface-neutral one; no prompt or check changed.
- **R2.** The arm runs only with `BENCH_AGENT_MCP=1`, so a missing variable spends nothing. Its
  config is asked of the demo first (`--mcp --print-config`). On 2026-10-12 R6 was not built, the
  demo printed nothing, and the config was derived from the shim the CLI arms run, `demo --mcp`.
  R6 landed the same day, and from then on the arm handed `claude` the printed config as written,
  naming the bin `demo-burgee`. That was the 2026-10-20 failure (R6 below). The config now keeps
  the printed name and arguments and starts the shim by absolute path. A dry check on 2026-10-26
  started the real demo's server from it, in an environment with no `demo-burgee` anywhere on
  `PATH`, and listed `greet`, `config_get` and `fail`. The printed config as written failed the
  same check with `spawnSync demo-burgee ENOENT`.
- **R3.** Per-reading medians, ranges, success rate and run count, and the `burgee-mcp ÷ burgee`
  tokens and turns ratios over the mapped tasks only. The verdict record is the median of the landed
  readings' ratios. It appears from the fourth reading, so `cli-vs-mcp-tokens` reads `unmeasured`
  until then. With an even count the median is the midpoint of the middle two: the suite's
  nearest-rank rule would always take the lower value, and here the lower value always favours MCP.
- **R6.** The first paid run of the arm (the 2026-10-20 weekly job, run 39407740629) never reached
  its server. All 15 transcripts open with the server `failed`. One run passed its check anyway,
  so the arm was gated like a CLI arm at 0.067 against 0.8. The gate failed the job, and the CLI
  arms' reading was lost with it. R6 makes each of those a named outcome: the preflight refuses a
  server that lists no tools before any spend; a run without the server is `mcp-unavailable` and
  in no median; and a broken or weak arm leaves no ratio and does not cost the CLI reading. Proved
  red on the 2026-10-20 harness (11 tests), green after.
- **R4.** `BENCH_AGENT_MCP` is `1` on `schedule` and on a `bench:agent` PR only, and only once
  the owner has set `B1_MCP_ARM=approved` (see Cost). A push to `main`, a
  manual dispatch and an unlabelled PR run the two existing variants. The lock evaluates the
  expression for every event, and widening it to `push` turns it red (proved). The weekly reading
  now lands too, as `<date>-<sha>-weekly-ci.json`, so it never overwrites a push reading of the same
  commit. Since 2026-10-27 a manual dispatch with the boolean `mcp-arm` input set (default `false`)
  runs the arm too and lands as `<date>-<sha>-dispatch-<run id>-ci.json`
  (D-20261027-b1-mcp-arm-owner-dispatch). The run id keeps three dispatches of one commit apart, and
  `priorReadings` counts the name as it counts a weekly one. The name check (`isLandedCi`) is a
  function rather than a module-level constant so Stryker can attribute it per test. Stryker, run
  by hand on that line, killed 14 of 14 mutants.

## Cost

**Approved and running since 2026-10-12**
([D-20261012-b1-mcp-arm-approved](../../decisions/D-20261012-b1-mcp-arm-approved.md)). The
first paid reading, 2026-10-20, spent 15 runs and 1,856,328 tokens. The CLI arms' 50 runs spent
5,639,658 tokens in the same job, so the arm cost 33% of them, under that decision's stop rule. It
was no reading (R6), so it counts toward nothing.

- **Per weekly reading, the arm adds 15 paid agent runs** (3 mapped tasks × 5 runs), on top of the
  50 that the scheduled B1 job already spends: 65 runs a week instead of 50, +30%. That is fewer
  than the 25 quoted in the intent, because two tasks are excluded by name.
- Each run is bounded the same way as the CLI arms: the task's `maxTurns` (12 or 15), a 300 s
  timeout, and the pinned `claude` on `claude-sonnet-4-5`. Each reading records the tokens per
  run.
- A PR labelled `bench:agent` spends the same 15 runs on top of its 50.
- Wall time: B1's job took 25–31 minutes on recent pushes. The extra 30% fits inside its
  60-minute `timeout-minutes`.
- R5 and `cli-mcp`'s fourth criterion need **four readings: 60 extra paid runs.** Since 2026-10-27
  the owner may dispatch them rather than wait for the schedule
  ([D-20261027-b1-mcp-arm-owner-dispatch](../../decisions/D-20261027-b1-mcp-arm-owner-dispatch.md)).
  A dispatch is the whole B1 job, 50 CLI-arm runs and 15 MCP-arm runs. The owner approved three on
  2026-10-27, at about 1.9M tokens each for the arm and about 6M in all.
- **Stopping it.** The arm runs only while the repository variable `B1_MCP_ARM` reads `approved`
  (Settings → Secrets and variables → Actions → Variables). Deleting it stops the arm at the next
  run, and every event then runs the two CLI arms only.

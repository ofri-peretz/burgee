**Superseded 2026-09-21: to be chased, not recorded.** The owner's instruction is that no failure stands — "every failure we must fix or improve until it reaches our own measurements satisfaction" — so the posture below is the wrong one and is kept only as the record of what was known. **What is known now.** The trigger is not CPU: sixteen busy loops did not reproduce it, and a `matrix.test.ts` run under them passed 23 of 23. It appeared six times while CI watches, `gh` polls and pushes were competing for process slots, and **not once in four consecutive clean `ci:local` runs** afterwards, which points at concurrent *spawns* rather than load — the same shape `exit-hook 17 / 21` and `conformance 121 / 122` showed the same evening. **One theory is refuted rather than open:** the file calibrates its deadlines from a measured cold start, so a loaded runner might have inflated them without bound; measured, a cold `node` goes 32 ms idle to 278 ms under sixteen loops, which puts `budget()` at about 1.1 s and not at minutes. **Named 2026-09-21, which is what every earlier occurrence lacked:** one run finally reported the case rather than the file — `the deadline, end to end (R2, Y10) > ignores SIGTERM: the parent still settles, timedOut is true, and the partial output survives`. The mechanism is the one the file's own header already describes. `beforeAll` measures a cold `node` once and every deadline is a multiple of it, so a calibration taken while the machine is briefly idle sets a budget that a later loaded run outruns: the stubborn child has not installed its `SIGTERM` handler yet, the first rung kills it by the platform's default action, and the assertion that its partial output survives fails. The file asserts that output line *first* because it is proof the child was armed — under load it is proof it was not. The fix that follows is a handshake: start the deadline when the child says it is armed rather than when `run()` is called, which is a change to `run()`'s test design and carries its own proof.

**No.** U12 is restated to the half the code delivers, and that half is **Built**. The first
outside adopter stays an open adoption measure in gap C3. It is not a gate on any release.

U12's design condition joined two things with "and":
- **The independence install test passes for every layer.** This is engineering, and it has been
  built since 2026-09-24. `scripts/independence-install-lock.test.ts` packs each published
  package, installs it alone with only the in-family packages it declares (`--offline`), imports
  every entry, and fails on any cross-package edge to an undeclared package.
- **The first adopter installs a layer alone.** This is an event in someone else's repository. No
  change to this code can make it happen, and its timing belongs to another project's
  maintainers. A trial on 2026-10-08 (the `burgee-u12-adoption-trial` memory) showed that
  pitching too early costs the only first impression.

Gating 1.0 on the second half would make a release depend on a stranger's merge button. D-170's
1.0 bar is about what we ship: the spec is built, each drop-in is level with its incumbent at
the latest release, and coverage is held. So:
- **U12 reads Built** on its first half, and the status row cites the lock.
- **The adopter** stays tracked as gap C3 ("a CLI we did not write, installing one layer
  alone"). The scheduled mcpc trial (2026-10-09) is the first attempt. When an adopter merges,
  C3 closes, and that is announced as adoption, not as a release condition.
- **burgee 1.0** waits only on U9: three consecutive weekly authoring evals at 9 of 10 or
  better. Week 1 met that on 2026-10-08 at 10 of 10; weeks 2 and 3 are due about 2026-10-15
  and 2026-10-22.

Owner direction, 2026-10-09: "keep pushing", accepting the plan's default to take U12 out of
the 1.0 gate.

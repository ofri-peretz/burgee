**Measured, named, and not changed tonight — the sync API is what blocks each one.** Scanning every entry point's startup graph after D-101 turned up two places where a *data file* is the majority of the bundle. **`paratext`: `schema.json` is 6,413 of 11,113 bundled bytes (58%)** — the family plugin schema, imported by `capability.ts` because `register()` validates every capability against it, and `builtins.ts` registers seven through the public `register` at module load. That is deliberate (flagstaff U4: "a built-in cannot grow a power a stranger's plugin lacks") and it means a program printing one hyperlink re-validates our own capabilities on every start. **`flagstaff/ora`: `spinners.json` is 31,188 of 55,467 (56%)** — `cli-spinners`' whole corpus, reached from `set spinner()` for the named case and exported as `spinners` because that is ora's own API. Neither can go lazy: `register()` is a synchronous public call and `set spinner()` is a **setter**, so an `await import()` is not available at either site, and both are the same class as `bellpull/cross-spawn` in the commander façade (D-102) — a contract bought with bytes. Reading the JSON from disk instead of inlining it would move the bytes rather than remove them and would break a bundled consumer outright. Recorded because the numbers are worth knowing and because the shape is now the repository's most common source of weight: **`paratext ÷ ansi-escapes` at 2.556 is 58% plugin schema**, and `.sdlc/PLAN.md` D1 already decided the foundation tier is compared against the incumbent's *tree*, where `paratext` is not the outlier this row makes it look. ora carries the identical corpus, which is why `flagstaff/ora ÷ ora` is 0.932 rather than 0.41

**It builds dotenv 18, and is level at 18.0.5: 179 / 179 against a control of 179 / 179. It does not build the vault, the `DOTENV_KEY` decryption or the tips, because dotenv 18 deleted all three.** This supersedes D-097 on one clause only, *"dotenv 61 = 27 `.env.vault`/`DOTENV_KEY`, which dotenv itself deprecated in favour of dotenvx and this package declines, and 34 needing `config()` to default `processEnv`"*, and the matching sentence in D-135's host note (*"27 vault/decrypt (declined), 2 dotenvx tips (declined)"*). The rest of D-097 and all of D-135 stand, and neither is edited.

**Why the answer is not "implement the vault".** The owner direction was to implement vault decryption exactly as dotenv does and to match the tips the suite asserts. That direction was written against dotenv 17.4.2. The bar it serves is level at the latest release, and the latest release is **18.0.5** (`npm view dotenv version`, 2026-10-01; 18.0.0 shipped 2026-09-17). dotenv 18.0.0 removed `decrypt`, `.env.vault`, `DOTENV_KEY`, `_parseVault` and the rotating tips from `lib/main.js`, and removed `test-config-vault.js`, `test-decrypt.js` and the two tips cases from its suite (upstream 4bb2dbd and the 18.0.0 release). So "exactly as dotenv does" now means `DOTENV_KEY` does nothing. A drop-in that decrypted a vault would do something dotenv 18 does not, the first time a migrating program had both `DOTENV_KEY` and a `.env.vault` lying around. `node:crypto` therefore stays out of the package entirely, which is a stronger form of the lazy-load the direction asked for.

The tips are the same case. dotenv 18's suite asserts the log line *without* tips: `displays the injected env message without tips` matches `^◇ injected env \(\d+\) from tests/\.env$` on `console.error`. The façade prints exactly that line. It advertises nothing, so there is no third-party product to note.

**What dotenv 18 changed, and what was built for it.**

- `parse(src, { fast: true })`: a second parser, dotenv's hand-written character scanner (`packages/seniority/src/dotenv-scan.ts`), ported line for line. The regex parser now expands `\n` and `\r` when a value *opens* with a double quote, closed or not (issue #1043, pinned by the suite). The previous port expanded only a matched pair.
- `config()` takes its defaults from `DOTENV_PATH`, `DOTENV_ENCODING`, `DOTENV_QUIET`, `DOTENV_DEBUG`, `DOTENV_OVERRIDE`, `DOTENV_FAST` and their older `DOTENV_CONFIG_*` names, with an explicit option over both. It reads `quiet` after loading, so a `DOTENV_QUIET` inside the `.env` counts unless the caller or the starting environment said. It reports `◇ injected env (n) from <paths>` on `console.error` and debug lines behind `┆` on `console.log`. Each file is populated with the caller's options, so `override` lets a later file win. `configDotenv` is exported.
- `seniority/dotenv/config`, the `import 'dotenv/config'` / `node -r dotenv/config` entry. It is quiet unless the starting environment says otherwise.
- `seniority/dotenv/cli`, dotenv 18's `dotenv run` (`cli.js` and `lib/spawn-command.js`). It loads `-f` files, forwards SIGINT, SIGTERM, SIGHUP and SIGQUIT to the child's process group, escalates repeated Ctrl-C to SIGTERM and then SIGKILL, and exits with the child's code or re-raises its signal. On Windows it resolves `PATHEXT` and escapes for the C runtime and for cmd, twice for a batch file. It takes the process from `runtime.ts` (`ambientProcess`, D-135's seam) and never names the global.

**The private-module cases.** At 17.4.2 six cases loaded `lib/cli-options` and `lib/env-options`. dotenv 18 deleted both. Its one private module is `lib/config-options`, loaded only by `test-config-options.js`, which the oracle classifies as internal and grades on the informational line. That line is **4 / 10 for both** the control and the target. The six `optionsFromEnv` cases fail against dotenv itself, because the published package ships only `dist/` and the module is bundled out of reach. The four cases in that file that spawn `require('dotenv')`, `import 'dotenv/config'` and the CLI pass for both. Nothing is excluded by title.

**Where the harness half landed (2026-10-06).** The `entries` / `selfExports` work below was written with this decision and then landed separately, in the compat-oracle lane, with the control fixes for boxen 9 and clack (D-20261006-flagstaff-boxen-9). This decision's PR carries only seniority, the claim (`GRADED`, `SUPPORTED_MAJORS`, `DROP_INS`) and the ratcheted baselines. Measured on that harness: dotenv 18.0.5 **179 / 179** against a control of **179 / 179**; dotenv 17.4.2 **107 / 141** against **141 / 141**.

**What the oracle needed.** dotenv 18's suite tests its build, not its source: it spawns `node dist/index.cjs run …`, preloads `dist/config.cjs`, and runs programs that name `dotenv` and `dotenv/config` from the repo root, where upstream answers by self-reference. Without help, 38 cases failed against dotenv itself. Two host fields carry it, and neither touches an assertion:

- `entries` writes each such file per run. On the control it is a symlink to the installed incumbent's own file, so `require.main === module` holds in dotenv as it does upstream. On a target run it is upstream's `index.js` pointed at the target.
- `selfExports` gives the vendored root the incumbent's name and an exports map of those entries, so the spawned `require('dotenv')` reaches whatever the run grades. Before it, the target run would have graded dotenv against itself. The oracle's resolver for packages installed beside a suite now anchors inside `node_modules`, where self-reference does not reach. A test in `grade.test.ts` fails without that change.

**Evidence.**

- **The grade.** Before: dotenv 17.4.2, target **106 / 141**, control **141 / 141**. After: dotenv 18.0.5, target **179 / 179**, control **179 / 179**, one Windows-only case skipped on both. The reference moved because the suite did: 42 cases added and 31 removed (the vendor diff).
- **dotenv 17 is graded and not claimed.** It is a `PREVIOUS_MAJORS` row (C1): **107 / 141** against a control of **141 / 141**. The 34, counted file by file from the raw TAP: 23 in `test-config-vault.js` and `test-decrypt.js`, which dotenv 18 removed; 2 that assert the tips, which 18 removed; 6 that expect the log line on `console.log`, where 18 writes it to `console.error`; and 3 in `test-config-cli.js` that preload 17's deleted `lib/cli-options` and `lib/env-options`. `SUPPORTED_MAJORS.dotenv` is `[18]`, so `burgee migrate` leaves a dotenv 17 project alone and says so under `offMajor`.
- **Held to dotenv, not to itself.** A differential fuzz ran random sources built from the characters dotenv's grammar turns on (quotes, backslashes, `export`, `:`, `#`, CR, LF, U+2028, NBSP, BOM) through dotenv 18.0.5 and seniority/dotenv, both parsers. 600,000 comparisons gave 0 differences. The only differences ever found are `__proto__` keys, which dotenv assigns to the prototype and seniority keeps as an entry, on purpose. `dotenv-scan.test.ts` pins 66 sources with values read off dotenv 18.0.5, and one source where dotenv's own two parsers disagree, pinned as they disagree.
- **Tests that can fail.** The scanner's two character tables are each checked over every code unit against the regular-expression parser; dropping U+3000 from the whitespace list or swapping `.` for `/` in the key table fails four cases (measured 2026-10-06, then reverted). Coverage stays at 100 / 100 / 100 / 100 for seniority.

**What level sets in motion (D-137).** `burgee migrate` now rewrites `dotenv` to `seniority/dotenv`, and `dotenv/config` and `dotenv/config.js` to `seniority/dotenv/config`. Those two are graded pairs because the suite reaches them by name. `FACADE_EXPORTS` carries both targets' names. The compatibility page, the host note, `GRADED`, `GRADED_VERSIONS`, `SUPPORTED_MAJORS`, the baselines and the docs restate the grade.

**What it costs.** Two new entries, `dist/dotenv-config.js` and `dist/dotenv-cli.js`, plus `dist/dotenv-scan.js` and `dist/dotenv-spawn.js` behind them. No other entry imports any of them, and `node:child_process` is reached only from `seniority/dotenv/cli`. burgee's bundle is unchanged, because burgee loads `seniority/config` and nothing of dotenv's.

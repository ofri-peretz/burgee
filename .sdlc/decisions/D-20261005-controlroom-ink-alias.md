**The line is `"ink": "file:./ink"`, pointing at a two-file package of the program's own that re-exports `controlroom/ink` at version 6.8.0. The two examples that use it are installed alone, never as workspaces. B4 sides may be several imports.** Measured 2026-10-05: `ink-spinner`, `ink-text-input` and `ink-select-input` run unmodified, 7 / 7; `examples/chat-cli-ink` passes 12 / 12; W1 0.745, W2 0.378 in bytes and 0.238 in packages, W3 (root) 0.048, W4 0.289 and 0.144.

**1. Not a bare `npm:` alias, because it names a package, not a subpath.** The spec (R17) says a `package.json` alias or `overrides`. `"ink": "npm:controlroom@…"` and `overrides: { ink: "npm:controlroom@…" }` both install the whole `controlroom` package under the name `ink`, so `import 'ink'` reads its `exports["."]`, the native API, and every ink component fails on its first named import. Nothing in npm's alias or override syntax selects a subpath, and a Node condition (`--conditions`) would also turn the program's own `import 'controlroom'` into the drop-in. So the line points at a directory the program owns: `ink/package.json` (`"name": "ink"`, `"version": "6.8.0"`, `"exports": "./index.js"`) and `ink/index.js` (`export * from 'controlroom/ink'`). The version is the ink API the drop-in implements, which is what makes it work: each component's peer range on ink (`>=4.0.0`, `>=5`, `>=5.0.0`) is met by the link, so npm installs no other ink — measured, the install holds no `ink` but the link. The re-export goes through the public `controlroom/ink` specifier, so it does not depend on the package's `dist/` layout. Rejected: shipping that directory inside the `controlroom` tarball (`"ink": "file:node_modules/controlroom/ink"`), because a `file:` path into `node_modules` does not exist until the install it is part of has run.

**2. The examples are not workspaces.** With `examples/ink-ecosystem` a workspace, npm 11.16 linked the root `node_modules/ink` to its shim and **dropped the real ink 6.8.0 `benchmarks` declares**: a link versioned 6.8.0 satisfies `"ink": "6.8.0"`, so npm deduplicated the registry ink into it, and B4 and B2 would have measured the drop-in against itself while `resolvePackage`'s version check passed. A shim at any other version only moves the problem: whichever `ink` takes the root, a component hoisted beside the other one resolves it. So the root `workspaces` excludes `examples/chat-cli-ink` and `examples/ink-ecosystem` (`!` patterns, which npm and turbo both honour), and `scripts/ink-alias-lock.test.ts` installs each as a user does — `controlroom` and its in-family closure packed from the tree, the registry packages from npm, into an empty directory — and runs its own `node --test`, asserting the pass count so a test file that stopped being found is a failure. The examples' checks are on `node:test` so a copied boilerplate needs nothing else installed. Each example's first cases check that every importer's `'ink'` resolves to its shim, because the behaviour cases pass on real ink too: the same files against `ink@6.8.0` pass every behaviour case and fail exactly the resolution ones.

**3. Ink has no `--json`.** R22's check list includes `--json`. Ink has no structured output to project — it draws frames — so `chat-cli-ink` refuses `--json` with exit 2 and points at `chat-cli`, whose native API writes NDJSON. A pipe gets Ink's own linear output (`isScreenReaderEnabled` when stdin or stdout is not a terminal), which writes each `<Static>` line once and no escape sequence, on real ink and on the drop-in alike. The terminal cases run under `CI=false`, as ink's own suite does: under `CI`, ink draws only the last frame.

**4. A B4 side may be several imports (W1, W2).** `EntryPair.ours` and `.incumbent` are a `Side`: one import, plus `with` (more imports of the same program, bundled as one, as `PARITY` stacks already are), `external` (ink's `react-devtools-core`, an optional peer behind `DEV=true` that no bundler resolves when absent; and React, for W3's "ink alone"), and `eager` (count every chunk, because `controlroom/ink` loads its peers through `import()` under top-level await and the axis's initial-load walk would leave those stubs out in our favour). Rows are named by `sideLabel` — the specifier, then each further package — which is the specifier for every one-import side, so no existing row, band or claim changes its name. W2 is `installed: true` on the W1 pair: `installedTree` walks both trees with one `seen` set and its size is the package count, the one mechanism added, and the pair gains `installed-packages` rows and two gated ratios. W4 is three B2 variants (`ink + react`, `controlroom/ink`, `controlroom`), which makes thirteen, so `ROUNDS` is 52. The incumbent cache in `run()` is keyed by what was bundled, not by package, because ink with React (W1) and ink without it (W3) are two measurements.

**5. Not built here: W3's demo half.** `examples/dashboard` is on `feat/controlroom-input`, not on this base. Out of tree, with the axis's flags, the dashboard bundled from that branch's sources is 44,809 B against 695,034 B for the Ink screen fixture (0.064).
